# Test performance audit

Audit date: 2026-08-10  
Scope: every tracked `*.test.*` and `*.spec.*` file; generated build output excluded.

## Executive summary

- **Baseline: 367 files audited:** 326 root Vitest files, 39 control-agent Vitest files, and 2 Playwright specs.
- **3,048 discovered test cases:** 2,459 root, 261 control-agent, and 328 Playwright project cases.
- **Baseline priority distribution:** 10 P0, 16 P1, 60 P2, 281 P3.
- **Largest systemic opportunity:** 170 root files appear not to need browser APIs and should be benchmarked in a Node-environment Vitest project instead of the global jsdom environment.
- **UI concentration:** 40 DOM suites took at least 1 second and are candidates for smaller fixtures, fewer full-page renders, or file-level splitting.
- **Integration concentration:** 14 filesystem/Git/process suites took at least 500ms; fixture reuse and fewer subprocess round trips are the safest optimizations.
- **Real waits:** 5 files contain at least 100ms of fixed/real waiting. Prefer observable readiness or fake timers where the wait is not itself the behavior under test.
- The two Playwright specs expand to 328 cases. Their full screenshot/video run was not timed because it requires the seeded screenshot build; the per-file recommendations are static and should be validated with Playwright's JSON/blob reporter.

Priority meaning: **P0** is a suite-level bottleneck or broad browser matrix; **P1** is a multi-second integration file or large fixed wait; **P2** is measurable but secondary; **P3** needs no immediate work.

## Improvements applied

- Root Vitest now discovers the same 2,459 tests exactly once across 211 general Node files, 15 component-adjacent Node files, and 106 jsdom files. Browser-only projects use threads; database and service tests retain process isolation after an all-thread run exposed a native exit-139 crash.
- The complete root suite passes with 2,458 passed and 1 skipped in **30.24s**, down from the audited **42.61s** run (about **29% faster**). The six additional files are parallel wrappers for the three largest UI suites; the test count is unchanged.
- The 47 Worktrees Page cases are split into four partitions (slowest measured partition: 4.10s versus the original 7.65s file), Telemetry into two (2.87s versus 4.84s), and Diffs into three (1.50s versus 4.04s).
- The control-agent codebase suite copies one clean Git template per test instead of replaying five setup subprocesses. In complete-suite profiling it fell from 10.46s to 8.75s. Shared worktree templates now also carry the signing configuration instead of rewriting it in eight tests.
- Credential database tests copy one schema template instead of creating and deleting a database directory and schema for every case. Their complete-suite file time fell from 1.89s to 1.36s.
- Worktree-watch shutdown now has an observable completion state and no longer spends 750ms proving a negative with a sleep. Command cancellation waits for the first uploaded output batch instead of sleeping 100ms.
- Screenshot capture replaces every 800ms settle sleep and each 300ms interaction sleep with fonts, animation frames, dialog visibility, and selected-tab state. This removes **262.8 seconds of aggregate fixed delay** from the four-project matrix before worker parallelism. The complete post-change capture passed all **324 cases in 2.1 minutes** across the four projects.

The detailed tables below preserve the pre-change profile so future runs have a baseline. Renamed case modules and their small test wrappers supersede the three original large UI file paths.

## Recommended optimization sequence

1. Split root tests into Node and jsdom projects. Start with the 170 statically identified files, verify them in batches, and keep DOM/API-dependent files in jsdom.
2. Reuse control-agent Git repositories and clones across compatible cases, especially sync, inventory, codebase, move, auto-sync, and checkpoint suites.
3. Split the largest page suites so Vitest can schedule them independently; also reduce oversized response fixtures and repeated full-page renders.
4. Replace fixed browser sleeps with route-specific GraphQL/text/readiness signals, and make the full four-project screenshot matrix selectable or shardable.
5. Keep timing telemetry in CI (Vitest JSON/JUnit plus Playwright blob/JSON output) and compare medians over multiple runs before and after each change.

## Method and limitations

- Vitest runtime is one complete local profiled run after the current fixes. File runtime includes hooks and assertions and is best used for prioritization, not as a stable benchmark.
- Static signals are heuristic. A Node-environment or fake-timer recommendation must be validated because imported code can depend on browser globals even when the test file does not reference them directly.
- Baseline Playwright case counts came from `playwright test --list`; the post-change 324-case capture spec was then run against the seeded screenshot build in 2.1 minutes. The four walkthrough/video cases were listed but not timed because their waits intentionally control recording pace.
- P3 means no material issue in this sample, not that the file can never regress.
